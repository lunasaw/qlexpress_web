## 二、规则特征分析

### 2.1 代码结构特征

通过分析典型规则文件，发现以下共性结构：

```groovy
// 1. Import 区域 - 大量依赖
import com.weidian.app24h.iot.plugin.*

// 2. 初始化区域 - 获取设备适配器和服务
DeviceAdapter deviceAdapter = CommonComponent.getComponent(DeviceAdapter.class)
DeviceService doorService = deviceAdapter.getDoorByNo(1)
DeviceService hornService = deviceAdapter.getInnerHorn()

// 3. 业务函数定义 - 可复用逻辑
function openDoor(...) { ... }
function playVoice(...) { ... }
function ackReport(...) { ... }

// 4. 主流程 - 条件判断和流程编排
if (startWatch) {
    if (networkAvailable) {
        // 有网流程
    } else {
        // 无网流程
    }
}
```

### 2.2 业务流程模式

#### 模式1：条件分支型 (IF-ELSE)

```
典型规则：openDoor.groovy, switchPress.groovy

┌─────────┐
│  开始   │
└────┬────┘
     ↓
┌────────────┐
│ 检查值守状态 │
└────┬───────┘
     ↓
   ┌───┐
   │ ? │ 是否开启值守
   └─┬─┘
  是 │ ├─ 否
     ↓   ↓
┌──────┐ ┌──────┐
│有网流程│ │直接开门│
└──────┘ └──────┘
```

#### 模式2：多路选择型 (SWITCH)

```
典型规则：blueTooth.groovy

┌─────────┐
│  开始   │
└────┬────┘
     ↓
┌────────────┐
│ 获取命令类型 │
└────┬───────┘
     ↓
 ┌───────┐
 │ type= │
 └───┬───┘
   ┌─┴─┬───┬───┐
   1   2   3   5
   ↓   ↓   ↓   ↓
 认证 开门 读状态 通知
```

#### 模式3：顺序执行型 (THEN)

```
典型规则：onWatch.groovy, offWatch.groovy

┌─────────┐
│  开始   │
└────┬────┘
     ↓
┌─────────┐
│ 重置状态 │
└────┬────┘
     ↓
┌─────────┐
│ 关闭门  │
└────┬────┘
     ↓
┌─────────┐
│ 播放语音 │
└────┬────┘
     ↓
┌─────────┐
│ 回包云端 │
└────┬────┘
     ↓
┌─────────┐
│  结束   │
└─────────┘
```

#### 模式4：并行执行型 (WHEN)

```
典型规则：openDoor.groovy 双门场景

┌─────────┐
│  开始   │
└────┬────┘
     ↓
┌─────────┐
│ 初始化  │
└────┬────┘
     ↓
  ┌──┴──┐  并行
  ↓     ↓
┌────┐ ┌────┐
│开门1│ │开门2│
└──┬─┘ └─┬──┘
   └──┬──┘
     ↓
┌─────────┐
│ 汇总结果 │
└─────────┘
```

## 四、可行性评估

### 4.1 技术可行性 ✅

| 评估维度 | 结论 | 说明 |
|---------|------|------|
| **脚本兼容性** | ✅ 可行 | Groovy 和 QLExpress 语法相近，迁移成本低 |
| **流程模式** | ✅ 完全支持 | LiteFlow 支持 THEN/WHEN/IF/SWITCH/FOR/WHILE |
| **上下文传递** | ✅ 可行 | FlowContext 可完全替代现有的参数传递 |
| **外部依赖** | ✅ 可行 | CommonComponent 机制可在脚本中直接使用 |
| **并发处理** | ✅ 支持 | WHEN 并行执行天然支持双门场景 |
| **热更新** | ✅ 支持 | LiteFlow 支持动态刷新规则 |

### 4.2 业务可行性 ✅

| 评估维度 | 结论 | 说明 |
|---------|------|------|
| **组件复用率** | 约 60% | 约 15 个公共组件可被多个流程复用 |
| **流程覆盖率** | 100% | 所有 29 个规则都可转换为 LiteFlow 流程 |
| **维护性提升** | 显著 | 组件化后修改影响范围可控 |
| **可视化价值** | 高 | 流程可视化大大降低理解成本 |

### 4.3 风险评估

| 风险 | 等级 | 应对策略 |
|------|------|---------|
| **性能损耗** | 中 | LiteFlow 调用有一定开销，需做基准测试 |
| **调试复杂度** | 中 | 组件分散后调试链路变长，需加强日志 |
| **迁移工作量** | 中 | 29 个规则 + 50+ 组件，预计 2-3 周 |
| **兼容性问题** | 低 | QLExpress 与 Groovy 语法基本兼容 |

### 4.4 优缺点分析

#### 优点

1. **组件复用**
   - `checkWatchStatus` 被 18 个规则使用 → 只需维护 1 份
   - `playAudio` 被 15 个规则使用 → 统一音频播放逻辑

2. **可视化编排**
   - 复杂流程如 `switchPress` (322行) 可直观展示决策树
   - 新人快速理解业务流程

3. **灵活组合**
   - 新业务场景可通过拖拽组件快速构建
   - 无需重新编写完整规则

4. **独立测试**
   - 每个组件可单独测试
   - 降低回归测试成本

5. **版本管理**
   - 组件独立版本控制
   - 流程独立版本控制

#### 缺点

1. **额外开销**
   - LiteFlow 运行时开销（约 5-10ms）
   - 上下文序列化/反序列化开销

2. **调试复杂**
   - 问题定位需跨多个组件
   - 需完善的执行追踪机制

3. **学习曲线**
   - 团队需学习 LiteFlow EL 语法
   - 需理解组件化设计思想

## 五、实施建议

### 5.1 分阶段实施

#### 第一阶段：试点验证 (1周)

选择 2-3 个中等复杂度规则进行试点：
- `onWatch.groovy` - 顺序执行型，复杂度中
- `offWatch.groovy` - 顺序执行型，复杂度中
- `forceLock.groovy` - 含条件分支，复杂度中

验证目标：
- 组件拆分是否合理
- 性能是否可接受
- 调试是否方便

#### 第二阶段：核心规则迁移 (2周)

迁移高频使用的核心规则：
- `openDoor.groovy` - 开门核心流程
- `switchPress.groovy` - 应急开关
- `microwaveSense.groovy` - 红外感应
- `blueTooth.groovy` - 蓝牙控制

#### 第三阶段：全量迁移 (2周)

迁移剩余规则，完成全部 29 个规则的组件化。

### 5.2 组件设计原则

1. **单一职责**
   - 每个组件只做一件事
   - 避免上帝组件

2. **输入输出明确**
   - 清晰定义 inputs/outputs
   - 使用 FlowContext 传递数据

3. **幂等性**
   - 组件可重复执行
   - 不依赖外部状态

4. **可测试性**
   - 组件可独立测试
   - Mock 外部依赖

### 5.3 命名规范

```
组件ID格式: {领域}_{动作}_{对象}
示例:
- door_open_single    # 单门开门
- door_close_all      # 关闭所有门
- audio_play_welcome  # 播放欢迎语音
- status_check_watch  # 检查值守状态
- report_ack_door     # 上报门状态
```
